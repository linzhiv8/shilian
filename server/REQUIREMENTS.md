## 1. 决策结论

| 决策 | 结论 | 连带影响 |
|---|---|---|
| **部署形态与用户规模** | **做成多用户产品，开放注册** | SSRF / 限流 / HTTPS / 安全响应头全部要做；补管理端用户 CRUD、密码重置、邮箱验证、审计日志 |
| **滑块验证** | **登录失败 3 次后才出滑块** | 正常登录无感，被撞库时才出现。**失败锁定 + 限流照做，滑块不替代它** |
| **认证方案** | **Spring Security** | 只启用核心能力（登录、PasswordEncoder、CSRF、会话管理、登出失效），不引入 OAuth2 与方法级安全的复杂配置 |

### 定为"多用户产品"后的增量需求

开放注册把下面这些从"可选项"变成"必选项"：

- **注册环节要有反滥用**：仅靠滑块不够，需 IP + 邮箱双维度频率限制
- **必须防用户枚举**：登录失败、注册重名、密码重置的返回信息要一致
- **需要审计日志**：谁在什么时候改了什么，出事要能追溯
- **需要管理端**：禁用账号、封 IP、查看异常登录
- **邮箱验证**：不做的话任何人都能拿别人的邮箱注册，后续无法找回密码

| # | 冲突 | 处置 |
|---|---|---|
| **1** | 系统从"本机单用户"变成"公网多用户"，SSRF、限流、HTTPS 从"不用管"变"必须做" | 安全工作量按最高档排（见第 4 节） |

## 4. 现状安全审计

### 已经做对的（不要重复投入）

- **SQL 注入**：`LinkRepository` 全用 `PreparedStatement` / `MapSqlParameterSource`；`orderBy()` 是 `switch` 白名单，用户输入进不了 `ORDER BY`
- **XSS**：全库无 `dangerouslySetInnerHTML` / `innerHTML` / `eval`
- **协议限制**：`Urls.normalize()` 只放行 http/https，`file://`、`jar://`、`ftp://` 已挡住
- **密钥管理**：`.env.properties` 已 gitignore；日志不打 Authorization 头

### C6 · SSRF（最高优先级，需求里没提但必须做）

`FetchService` 直接 `Jsoup.connect(url)` 且 `followRedirects(true)`。用户提交任意网址，服务端就去抓。多用户公网部署下这是**可利用的真实漏洞**：

- `http://127.0.0.1:8080/` → 探测本机其他服务
- `http://192.168.x.x/` → 扫内网
- `http://169.254.169.254/` → 云主机元数据（可拿临时凭证）
- **DNS rebinding** → 校验时解析到公网 IP，实际连接时解析到内网

防护要求：解析域名后**校验 IP**、拦截内网段（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`::1`）、**每一跳重定向都重新校验**、限制响应大小与超时。

### C4 · 越权访问

所有查询强制带 `user_id`。两条纪律：越权返回 404；用 ArchUnit 禁止 `LinkStore` 出现不带 `UserId` 参数的查询方法签名（管理端除外）。

### correction 跨用户污染

`correctionsBlock()` 现在全局聚合。多用户后必须按 `user_id` 过滤，否则 A 把"技术博客"改成"商业·行业"之后，B 分析同类内容也被带偏——**不报错、只让结果悄悄变差**，正是这个项目最警惕的那类问题。

### 限流为什么这么写（C14）

**滑动窗口而不是固定窗口。** 固定窗口在切换的那一刻会漏：
1 分钟的窗口，第 59 秒打满、第 61 秒又能打满，两秒内放过了两倍的量。
按 IP 限流这种用途，攻击者只要卡着边界打就行。

**计数放内存、重启清零，是刻意的。** 限流保护的是「刚刚有人刷了」这个短时状态，
重启后从零开始完全合理；持久化反而会引入「服务重启后仍拒绝正常用户」这种更难解释的问题。

**窗口边界用半开区间 `[t, t+W)`，秒数向上取整。** 这两件事必须配套：
写成 `>` 再配整数除法向下取整，客户端按提示等满 60 秒回来，
正好落在「还没出界」的那 1 毫秒里，又被拒一次，提示变成「再等 1 秒」。
用户看到的是「它说话不算数」。（原先有一个 `RateLimiterTest.reportedWaitIsActuallyEnough`
专门守这条，但那个测试类随 `src/test/` 在 2026-09-18 清理时被删了——**目前这条边界没有自动化验证兜着**，
补它属于 R-11 的范围。）

**注册要两个维度。** 只按 IP 限挡不住换 IP 的人——代理池很便宜，
而「每个邮箱只试一次」的攻击者在 IP 维度上看起来完全正常。
邮箱维度的 key 必须先 `trim + toLowerCase` 规范化，否则改个大小写就是一个新桶。

**邮箱维度的代价说清楚**：别人可以用你的邮箱把额度打满，让你一天注册不了。
所以额度给得宽松（5 次/天），正常人手滑重试碰不到，挡的是「反复」。

### 可观测怎么做的（阶段 2）

**traceId 必须跑在 Spring Security 之前。** 用 `FilterRegistrationBean` + 最高优先级
注册在 servlet 容器层，而不是给过滤器加 `@Component`——后者会被 Spring Security
收进它自己的过滤器链并排在最后，于是**被 401 拦掉的请求压根拿不到 traceId**，
而「登录为什么失败」恰恰是最需要追踪的场景。实测：401 响应同样带 `X-Trace-Id`。

**分段耗时解决的是「该动哪一头」。** 分析链路里抓取和调模型都可能慢，
但对策完全不同（换网络 vs 换模型/调提示词）。实测一次：
`分析完成 · 3166 ms（抓取 914 · 提示词 1 · 模型 2246）· 2 次调用 · 7062 token`
——模型是大头，而且还重试了一次，两个信息都是以前拿不到的。

**`/api/health` 从「配置好了没」升级为「现在能不能用」。**
熔断打开时 `status` 降为 `degraded`，另外报剩余分析并发。

真实库已验证：迁移版本记录在 `schema_version` 表，19 条老数据一条没丢且已划归首个账号；
跨用户隔离、失败锁定、SSRF 拦截均实测通过。

### SSRF 防护怎么做的（C6）

`infrastructure/security/SsrfGuard`。三条规则，每条都对应一个真实的绕过手法：

1. **只校验域名没用** —— 攻击者把域名 A 记录指向 `127.0.0.1`，域名本身完全正常。
   所以解析后的**每一个** IP 都要过检查（一个域名可能有多个 A 记录，
   只看第一个不够）。
2. **只校验第一跳没用** —— 给个正常公网网址让它 302 跳到内网。
   所以 `FetchService` 关掉了 `followRedirects`，手动跟，**每跳都重新校验**。
3. **IP 有等价写法** —— `2130706433`、`127.1`、`[::1]` 都指向本机。
   所以不自己解析字符串，一律交给 `InetAddress`——它认识所有这些写法。

**已知限制：挡不住 DNS rebinding**（校验时解析到公网、连接时解析到内网）。
彻底解决要在 socket 层绑定校验过的那个 IP，还要处理 HTTPS 的 SNI 和证书，
代价远超这个阶段该承担的。缓解是缩短校验与连接之间的时间窗。

### 隔离怎么做到的

新增 `CurrentUser` 端口（`domain/port/`），由 `LinkRepository` 内部调用，
**每一条 SQL 都带 `user_id` 条件**。

选它而不是"每个方法传 `userId` 参数"，是因为后者把"别忘了按用户过滤"
变成每一处调用点都要记得做一遍的事——漏一处就是一次数据泄露，
而且不报错、不告警。代价是数据层多一个隐式输入，单测要喂假实现。
控制器因此一行没改。

### 已知缺口

多数是刻意留的（说明理由），少数是这次才发现的——第 4 条就是。

1. **CSRF 关闭**（C9，阶段 5）。前端还没有取 XSRF token 的逻辑，
   开启会让所有 POST 立刻 403。缓解：会话 Cookie `SameSite=Lax`。
2. **改密码不会踢掉其他设备**。需要 `SessionRegistry`，
   而它只在走框架自带登录过滤器时才填充——这里登录是手动调 `authenticate`，
   不经过登记。补齐要改登录方式或自建登记表。
3. **限流按 `getRemoteAddr()`，上反向代理之后会失效**（C14 的已知边界）。
   产品方向是公网多用户，上线必然要过 nginx；到那时 `getRemoteAddr()`
   返回的是代理自己的地址，**所有人共用一个限流桶**——一个 IP 打满额度，
   全体用户被挡在门外，限流器直接变成拒绝服务工具。
   正确做法是在代理层配可信代理列表，由代理把真实地址写进一个受信任的头。
   **上代理之前必须先做掉。**
4. **邮箱大小写**（本次做限流时一度判错，已纠正）。原先这里写的是
   「库里原样存储、精确匹配，所以 `A@x.com` 和 `a@x.com` 会被当成两个账号」——
   **这条与 DDL 矛盾**：`app_user` 表是 `COLLATE=utf8mb4_unicode_ci`，
   而 `email` 列（`V1__baseline.sql`）没覆盖 collation，于是继承 `ci`（大小写不敏感）。
   所以 `WHERE email = 'a@x.com'` 会命中 `A@x.com`，唯一索引 `uk_app_user_email`
   同样不区分大小写，**插不进第二条大小写变体**——「一个人占两个号」在存储层根本不成立。
   结论：**不需要专项迁移**，也不需要合并冲突行。只做两件小事：在生产库跑一次
   `SHOW FULL COLUMNS FROM app_user LIKE 'email'` 确认 collation；把存量邮箱统一小写一次
   （为展示整齐，并入 V3 顺手做）。限流的 key 本来就自己做了规范化，不受影响。
5. **邮箱验证 / 重置密码未做**（阶段 6）——依赖待确认项 1（邮件服务）。
   在此之前，忘了密码没有任何自助途径（原先的救急工具 `tools/user.sh` 已删），
   只能手写 SQL 改 `app_user` 表的密码列，哈希用 `BCryptPasswordEncoder(12)`。
6. **改密后同设备会话继续有效**，换的是 sessionId 而不是整个会话，这是防会话固定所需。
7. **DNS rebinding 未防**（见 C6 那节）。其余 SSRF 路径已封。
8. **没有指标导出、没有分布式追踪**。当前只有日志 + traceId，
   足够定位「这一次请求发生了什么」，不足以回答「过去一小时的整体情况」。
   个人自用阶段先不引入 Prometheus / OpenTelemetry。

### 老数据的归属

V2 迁移只改结构不划归属，19 条老数据 `user_id` 为 NULL。
**第一个注册的账号**调用 `claimOrphans()` 把它们接过去，
同时认领 `correction` / `ai_log` / `weekly_digest` 里的 NULL 行。
判断条件是 `countAll() == 1`，第二个账号不会触发。
