# 拾链 · 个人网址库

发现一个有意思的网站 → 丢个链接进来 → AI 补完标题、摘要、备注、分类、标签。
你只做点选，不做填空。

> 当前状态：**前后端已接通，回顾机制和周报也做完了，可以用起来了。**
> 前端 Vite + React 19（在 `web/`），后端 Spring Boot 3 + MySQL（在 `server/`），两者平级。
>
> 数据库**只有 MySQL 一个**：本地开发和部署用的是同一份配置、同一条代码路径，
> 区别只在 `.env.properties` 里填的地址。所以「本地跑通」和「部署起来能跑」
> 验的是同一件事，不存在「本地是另一个库」这种分支。

## 跑起来

要开两个进程。

后端：

```bash
cd server
cp .env.properties.example .env.properties   # 填 DEEPSEEK_API_KEY 和 MySQL 连接（见文件里的注释）
./mvn.sh spring-boot:run                     # 127.0.0.1:8080
```

MySQL 那三项的名字是 `SPRING_DATASOURCE_URL` / `_USERNAME` / `_PASSWORD`
（大写+下划线，和 `application.yml` 里的占位符同名才接得上；
写成 `spring.datasource.url` 不生效而且不报错）。不填就用默认值，
指向本机 3306 上的 `shilian` 库。

**本地开发也要有一个能连的 MySQL**（本机装一个，或者直接用服务器上那个）。
没有「不装数据库也能跑」的开关——那需要第二套 SQL 方言，而它带来的麻烦
比省下的安装步骤多：它验不到 MySQL 特有的行为，却会因为「它也认」而让一批
旧方言在测试里全绿。所以这个工程只留一条路。

### 连不上 MySQL 时看启动日志

启动失败时，框架的失败分析器会把整个异常堆栈替换成一段可读提示——
里面有根因，和一张「域名 / 端口 / 防火墙 / 账号 / 库 / 认证插件」六项对照表。

JDBC 的报错文本对定位问题几乎没有帮助——端口没开、防火墙丢包、host 没授权
全都长成一句 `Communications link failure`。

**启动阶段连不上时，不用自己想起来去跑它**：`DatabaseUnreachableFailureAnalyzer`
会把那 60 行 Spring 堆栈换成一段「根因 + 是哪一层 + 怎么办」的提示，
其中第一条就是让你跑这个脚本。这也是为什么启动失败时看不到 `StartupSelfCheck`
的输出——那个类是 `ApplicationRunner`，跑在容器刷新之后，
而库是在刷新过程中（`Migrations` 的 `@PostConstruct`）就去连的，它根本没机会执行。

**语义搜索要额外配一个向量服务**（可选，不配的话那个按钮是灰的，其余功能不受影响）。
DeepSeek 只提供对话接口，**没有 embeddings 接口**，所以向量必须来自别处。
协议按 OpenAI 的 `/embeddings` 写的，所以选哪家只改三个值：

```bash
# 方案一：本地 Ollama（零账号、离线、免费，推荐）
ollama pull bge-m3
# EMBEDDING_BASE_URL=http://127.0.0.1:11434/v1
# EMBEDDING_MODEL=bge-m3
# EMBEDDING_API_KEY=ollama        （Ollama 会忽略这个值，但字段不能空）

# 方案二：硅基流动（有免费额度，中文检索效果好）
# EMBEDDING_BASE_URL=https://api.siliconflow.cn/v1
# EMBEDDING_MODEL=BAAI/bge-m3
# EMBEDDING_API_KEY=sk-xxx
```

前端：

```bash
cd web
npm install
npm run dev                                  # 127.0.0.1:5178
```

然后打开 http://127.0.0.1:5178/

**忘了启动后端也不要紧**——前端会直接告诉你「后端没连上」并给出启动命令，
不会静默失败或者报一个看不懂的错。

## 装上书签小工具（强烈建议）

打开 http://127.0.0.1:5178/bookmarklet.html ，把那个按钮拖到书签栏。

之后在任何网页点一下书签，就会跳到拾链并自动开始分析当前页。
从「复制网址 → 切窗口 → 粘贴 → 回车」四步变成一步。

它是怎么做到的：本质上只是一个指向 `/?url=<当前页>` 的普通链接。
没有装扩展、没有后台服务、没有跨域请求，就是一次普通页面跳转。

| 挑备注 | 抽屉里「挑一句当备注」，三句选一句（默认选第二句） |

| 排序 | 顶部右侧：最近收藏 / 星标优先 / 最久未看（语义模式下失效并变灰，会说明原因） |

| 打开原站 | 点条目标题或右侧箭头，顺带记录「已打开」 |

## 回顾：这个产品最容易做废的地方

需求文档里写着「这条如果做不好，前面所有功能都是白做的」。绝大多数书签工具
最后都变成数字坟场，因为用户永远在存、从不回顾。

**为什么是随机抽 3 张，而不是「最久的排最前」。** 按时间排的队列有个致命问题：
如果最前面那几条恰好不感兴趣，队列就**冻住了**——天天打开看到同样几条，
很快连这个入口都不点了。随机则每次重抽，代价是某条可能等得久一点，
但池子只有几十条，它不会消失。

**为什么一次只给一张，而不是列三张。** 列出来就会被当成又一个列表划过去，
而「当列表划过去」正是问题本身。一次一张，注意力被强制放在这一条上，
卡片也能做大——把**你当时写的备注**摆在最显眼的位置。备注才是唤醒记忆的东西，
标题只会让人觉得「嗯，好像存过」。

**为什么动作要给到四个。** 回顾的死穴是「看完了不知道干什么」。如果只能打开看看，
用户扫一眼关掉，这条下次还在队列里——那就变成反复提醒同一件事，
很快就会连这个模式都不进了。四个动作对应四种真实态度，**每一个都会让它离开队列**：

| 动作 | 效果 | 还会回来吗 |
|---|---|---|
| 打开看看 | 写 `last_opened_at`，把计时器归零 | 会，7 天后 |
| 留下 | 加星，退出队列 | 不会 |
| 看过了 | `status = 'read'` | 不会 |
| 删掉 | 删除 | —— |

注意「打开过」和「看过了」是两件不同的事，不能合并。前者是「我瞥了一眼」，
后者是「别再推给我」。少了后者，用户处理完一圈，下周看到的是同一批东西。

**侧栏那个数字由服务端算。** 前端自己拿全量列表过滤（排除星标、已用、已读，
还要按闲置天数比较）等于把筛选条件抄了第二遍，一漂就会出现「侧栏说有 5 条、
点进去只有 3 条」。所以单独开了 `/api/review/count`，它和队列用的是**同一段
SQL 条件**（`LinkRepository.REVIEW_WHERE`）。

## 周报：缓存必须能被数据作废

需求写的是「每周摘要（AI 写的，不是列表）」，所以主体是那段话，数字放下面当佐证。

摘要按 ISO 周缓存（`2026-W38`），不然每打开一次就花一次 token。但**光有周键不够**，
这里踩过一个坑：摘要写「这周存了 3 条」，下面的统计却写着 6。

原因是窗口是**滑动的最近 7 天**，不是固定的一段历史——用户这周每存一条，输入就变了。
所以现在缓存里连同一份**数据指纹**一起存（`WeeklyDigestService.fingerprint`：
对喂给模型的那段用户消息取 SHA-256）。读缓存时对一下指纹，对不上就重写。
用一个只给自己用的工具，看到「摘要和数字互相打脸」是致命的。

指纹塞在缓存 JSON 的 `_fp` 字段里，而不是单开一列——`schema.sql` 是
`CREATE TABLE IF NOT EXISTS`，加不了列，而这个库已经跑起来了。

**AI 挂了不会让整页挂掉。** 统计才是主体，摘要只是加值，所以调用失败时降级返回
统计 + 一句说明，而不是抛 502。

## 补正文：重分析不能复用「改一下」那条路

一张当初没抓到正文的卡片，存下来之后就再也没机会补上了——卡片上只有一句摘要。
这是全应用最后一个「用户遇到问题却无解」的场景。

入口在卡片底部（只在 `needsReview` 的卡片上出现）。点进去不是直接重跑，而是先问
**正文从哪来**：贴进来，还是「手里没有正文，先重新抓一次」。理由很实际——用户点这个
按钮往往是因为正文没抓到，如果他手里也没有正文，替他去抓一次大概率还是抓不到，
等于白花一次调用。

出草稿之后仍然走「看一眼再替换」这条老路（和新建收藏同一套确认界面，连备注
默认选第二句的规则都一样）。多出来一句提示：

> 应用后会重写这条的标题、摘要、备注、分类和标签；**加星、已用、收藏时间都不动**。

这句话不是客套。**补正文只该换掉 AI 那部分产物**，而 `url` 是这条记录的身份，
`starred` / `status` / `created_at` / `last_opened_at` 是用户跟它的关系——
重分析一个都不该碰。所以后端专门有个 `LinkRepository.Reanalysis` 记录，
而不是复用 `NewLink`：让「这次操作不许碰哪些字段」变成类型层面的事实，
而不是靠写的人记得。

**为什么不能直接用 `PATCH`。** 两个理由，第二个更要紧：

1. `PATCH` 只认 `EDITABLE` 白名单，而这里要写的是 `title` / `snapshot_text` /
   `ai_raw` 这类「AI 的产物」，本来就不该让前端随便改。
2. `PATCH` 会往 `correction` 表记一条「AI 判 X → 用户改成 Y」。而补正文
   **不是用户在纠正 AI**，是 AI 拿到了更好的输入重新判了一次。那张表会被拼进
   之后每一次分析的提示词，当作「用户真正想要什么」——把模型自己的新输出塞进去，
   等于让它照着自己的影子学习，而且会一路放大。

界面上还有一处细节：**用户原来写过的备注会被插到候选的第一位并默认选中**，
带一个「你原来写的」角标。否则用户一进来看到三句新备注、随手挑一句，
就把自己当初写的那句无声丢掉了。

## 编辑：网址为什么是「主动不做」

条目悬停时右侧有个铅笔，点开复用同一个抽屉，切成编辑模式。能改标题、摘要、备注、
分类、标签；**网址改不了**，而且这是有意的。

网址决定了当初抓的是哪个页面。改掉而不同步重跑分析，标题和摘要就变成在描述另一个网站。
所以不是漏了，是主动不做——并且在界面上把话说清楚：「真要换，重新存一条、把这条删掉更干净」。
不说的话，用户会绕着面板找一圈输入框，最后以为功能坏了。**「不支持」和「看起来像坏了」是两回事。**

**编辑走 `PATCH`，补正文走 `/reanalyze` + `/apply`，两者不能混。** 判据是
「用户有没有表达偏好」：编辑是用户亲手把 AI 的判断改成他要的，**必须**记进 `correction` 表
（那是调提示词最有用的证据）；补正文是 AI 拿到更好的输入重新判了一次，
**绝不能**记——记了等于让模型照着自己的影子学习，还会一路放大。

**用户手写过的备注必须被保住。** `noteOptions` 里只有 AI 那三句，用户手写的那句不在里面。
编辑时如果只渲染三句候选，他一保存就把自己写的话无声丢掉了。所以打开面板时把
`target.note` 插到候选第一位、标「你原来写的」、默认选中。
编辑的 payload **只发 `note` 不发 `noteOptions`**（AI 的候选不该被手写句污染），
所以库里候选永远是那三句、手写句每次重新拼进去——这段逻辑因此是幂等的。

## 语义搜索：惰性补齐，不维护索引任务

搜索框旁边那个「语义」按钮，用来按意思找东西——不用记住当初存的时候是什么标题。

**为什么不用「先建索引再搜」。** 个人库的量级（几百到几千条）不值得维护一个后台索引任务：
它要么得有个定时器、要么得在保存时异步触发，两条路都会引入「索引落后于数据」的状态，
而搜索结果的诡异程度和这个滞后成正比（刚改完标题，搜新标题搜不到）。

这里改成**惰性补齐**：搜索时看哪些记录的文本变了、没有向量，批量补上再排序。
第一次搜会慢一点（多一次批量调用），之后每条都命中缓存，一次调用搞定。
界面上会直说「这次慢一点，是因为刚给 N 条记录算了语义索引」。

**什么算「变了」。** 每条记录存了一个 `text_hash`——「可被搜到的文本」的 SHA-256。
文本没变就不重算。这个判据不能简化成「表里有没有这一行」：用户改了标题之后行还在、
指纹变了，只看有没有行就会拿旧向量去搜新文本，表现为「刚改完标题，搜新标题搜不到」。

**模型和维度必须存下来。** 换一个 embedding 模型之后，新旧向量**不在同一个空间里**，
算余弦得到的是垃圾——而且不报错，只会让结果悄悄变差。所以 `link_embedding` 表里存了
`model` 和 `dim`，查询时按模型过滤，换模型时旧行自然落进「需要重算」那一类。

**「一条都没命中」不能返回空。** 那是语义搜索最典型的失败方式：用户明明记得存过，
搜完一条都不给，他得出的结论是「这功能坏了」，而不是「我搜的词不对」。
所以低于阈值时会退回「最像的 3 条」并标注 `fallback`，界面上说明「没有很接近的，下面这几条是相对最像的」。

**`min-score` 是唯一需要校准的数字。** 默认 0.35 是个估计值。校准方法写在
`application.yml` 的注释里。调高不会让结果变空（有兜底），所以宁可先调高一点。

**连接纪律。** 这条链路上要调外部 API（几百毫秒），而数据库连接是有限资源。
所以流程刻意分成「读库 → 调 API → 写库」三段，中间不持有连接——
这几个方法上**没有** `@Transactional`，一旦加上，那几百毫秒会把连接和事务一起占住。

换 MySQL 之前这条纪律更硬：SQLite 是单写入者模型，池子只能开 1 个，
占住就等于全站排队。现在池子开到 8，占住一个不会立刻卡死别人，
但「跨网络调用持有事务」仍然是错的——事务开得越久，锁持有越久、回滚代价越大。

## 几个实现上的选择

**筛选全在客户端做。** 侧栏的领域/用途计数本来就需要全量数据，所以列表无论如何
都要整个拉回来；既然数据在手，搜索框边打边筛就不该再走一趟网络。
代价是数据量——个人库到几千条、响应体到几 MB 时该换成服务端筛选
（后端 `/api/links` 的 `domain` / `purposes` / `q` / `sort` 参数已经就绪），
再单独加一个返回计数的接口。

**前端用相对路径 `/api/...`，靠 Vite 代理转发。** 比硬编码后端地址好：
换端口只改 `vite.config.ts` 一处，将来同源部署也不用动代码。
（后端也配了 CORS，那是直连时的兜底。）

**「没连上后端」的判定不看状态码，看响应体是不是 JSON。**
这个坑是实测才发现的：后端没起时 Vite 代理返回的是 **502 + 纯文本**，
状态码不是 0。如果只看状态码，用户会看到「请求失败（HTTP 502）」这种技术黑话。
而我们自己的后端任何情况下都返回 JSON，所以「响应体不是 JSON」才是可靠信号。

**枚举中文名以服务端为准。** 前端为了配色仍保留一份 `DOMAINS`，
所以有走偏的可能——之前 `biz` 的标签就是这么漂掉的（前端写「商业·资讯」、
服务端早已改成「商业·行业」，直接导致技术博客被判错类）。
现在启动时会拿 `/api/meta` 比对一次，不一致就在控制台报出来。

**「已用」是状态不是用途。** 服务端统一归位：`purposes` 里收到 `used` 就摘掉，
改成 `status='used'`。卡片上单独渲染这个标记。

**抓不到正文时，给的是补救入口而不是一句「可能不准」。** 这是全应用唯一一个
「用户遇到问题却无解」的场景：SPA、需登录、Cloudflare 的站点抓不到正文是常态，
而他自己的浏览器里明明能读到内容。让他贴进来，我们照常分析。

几个刻意的选择：

- **贴了正文就不再抓取。** 他之所以会贴，正是因为抓取失败了；再等 20 秒去撞同一堵墙
  没有意义，而且他贴的内容比抓取结果更完整。实测贴正文的整轮分析只要 **2 秒**，
  而带抓取的要 4–30 秒。
- **正文来源做成一等字段**（`bodySource`）。因为两种情况下「缺什么」是相反的：
  抓取失败缺正文（有标题和描述），贴正文缺元信息（有正文，没标题）。
  只看 `fetchOk` 分不出来——贴正文时抓取根本没发生。前端要靠它决定显示哪种提示。
  （`fetchOk` 的含义是「拿到了可用正文」，贴正文时也是 `true`。)
- **提示词里专门加了「正文完整但标题描述没取到」这一档。** 原来只有三档，
  这个情况无处可落，模型只能自己猜，落到了「正文缺失」那档——于是用户刚贴完正文
  补救，又看到卡片标着「待补」。加上这一档后，同一个用例的置信度从 0.72 升到 0.85，
  `needsReview` 从 `true` 变成 `false`。
- **标题交给模型从正文推断**，不硬编一个「未知」。它拿到的正文是完整的，推出来的
  比我们瞎猜准（实测「Vector 日志采集工具」）。标题在保存前是可编辑输入框，
  用户扫一眼就能改，所以不值得为「标题是我猜的」降置信度。

**错误码要能指向正确的方向。** 后端所有失败都走同一个出口，每种给一句人话。
这里踩过两个坑，都不是「崩了」而是「安静地骗人」：

1. 路径写错（`/api/review` 这种）和参数类型写错（`?days=abc`）原本会落到兜底分支，
   变成 **500 + 一句「服务出错了」**，还往日志里打一整条堆栈。
   排查时会以为是后端代码有问题，其实只是前端拼错了路径。现在分别是 404 和 400，
   并且把出错的参数名直接说出来。
2. 分页参数原本只写了 `Math.min(limit, 20)`。少了个下限，`limit=-5` 就原样落进 SQL——
   在 SQLite 上这表示**不限量**，一个「最多 3 条」的接口会把整张表倒出来；
   换到 MySQL 之后则是语法错误，直接 500。两边表现不同，但都是错的。
   这种错不报错、不崩，只在某天突然变慢（或者突然全挂），极难往回追。
   现在两头都夹（`clamp(v, 1, 20)`）——但没有自动化的回归守护，改钳位逻辑时要自己盯。

## 设计约定（改样式时请遵守）

界面走的是「杂志感」：纸面底色 + 衬线标题 + 克制的彩色，主体是**文字列表**而不是卡片网格。改样式前先读这一节。

**为什么是列表不是卡片。** 收藏的是网址，没有图。卡片版式逼着你去造一个 16:9 封面，
而封面里只能填色块和字母——为了维持"卡片感"去填一个假封面，是拿内容迁就版式。
而且找东西时，列表的垂直扫描比网格的 Z 字扫描快得多（这是定位任务，不是浏览任务）。

- 颜色只用 `index.css` 里的 CSS 变量，不要写死色值。领域色统一走 `--d-{color}-tint` / `--d-{color}-deep`，深浅色自动切换。
- **没有侧栏。** 录入、筛选、回顾与周报入口、主题切换全在顶栏（`TopBar`），内容区全宽 880px。
  曾经有过 236px 侧栏：它和顶栏、内容区是三层不同底色，一眼能看出是"拼起来的"；
  更要紧的是它用了和卡片同级的 `surface`，等于在跟几百条内容抢视觉层级。
- **分层只有三级**：`canvas`（纸）→ `sunken`（浅凹，比如输入框和标签）→ `surface`（卡片/抽屉）。
  `canvas` 比中性灰暖一档（浅 `#fbfaf9` / 深 `#0c0b0d`），只暖这一档——偏色重了会把十个领域色全部带脏。
- **领域色在列表里只是一条 3px 竖线。** 它是索引不是主体。做成大色块的话，十个领域色等于每条都在喊。
- **衬线字（`font-serif`）只用在四类地方**：视图大标题、列表标题、用户手写的备注、统计数字。
  正文、标签、元信息一律无衬线。备注额外加斜体和左侧细线——它是用户亲手写的，
  必须和上面那段 AI 生成的摘要一眼分得开。
- 字号层级只有三档：16 / 13.5 / 12（辅助 11）。字重只有 400 和 500。
  - 视图大标题（26）和回顾标题（32）不受这三档限制，它们是版面标题，不是列表项。
  - 列表标题 17px，是这一屏的视觉重心。
  - 小标（领域/用途这类）最小 11px，字距 0.08em。中文不要再往下压。
- **accent（indigo）只在真正需要它跳出来的地方用**：主按钮、链接 hover。
  成排的选中态（chips）用 `ink`——紫色在暖纸面上是唯一的冷色，一排十几个会把整条拉回"工具界面"的观感。
- 间距用 4 的倍数。圆角 12px（卡片/抽屉）、8px（内部元素）、999px（chips 和主按钮）。
- 动效只保留 hover 微反馈和进场淡入，不要加更多。
- 骨架屏（`SkeletonList`）要跟真条目同形状：3px 竖线 + 标题 + 两行摘要。
  形状对不上，加载完那一瞬间会跳一下。

## 还没做

- 语义搜索**只覆盖标题/摘要/备注/标签/分类**，不覆盖正文快照。想搜「正文里那句话」搜不到
- 移动端适配
- 全文检索用 `LIKE`，中文长文本上到几千条后应该换 MySQL 的 `FULLTEXT` + ngram 分词器

- 向量是内存暴力余弦（几千条 × 1024 维 ≈ 十几 MB，算一次几毫秒）。到几万条时再说，
  那时该考虑 MySQL 8.4 的 `VECTOR` 类型或外挂一个向量库，而不是优化现在这个循环
